# Issue #83 validation: original external-firmware startup

Related to #83 and #17. This change proves a bounded synthetic firmware-to-disc
path and fixes medium retention at external cold reset. It does not establish
stock Sega BIOS boot, commercial-game support or completed hardware conformance.
The [startup contract](external-startup.md) lists the primary revisions, checked
printed/PDF pages, stages, hardware accesses, deadlines and conventions.

## Baseline before the production change

Inherited production code is main `8f1cdc14031009a190d9760f6ea3346ceafc8831`
(the Run's administrative commits do not change it). The original harness was
constructed before editing production code. The first firmware boot already
completed the SMPC/SCU/CD sequence and executed the actual first-read program.
The specific observable barrier was **cold restart ejecting the selected medium**,
not a claim that every supported startup register was missing.

An initial fixture assertion used control/ADR 40 instead of data-track 41; that
fixture mistake was corrected before identifying the production failure. The
final unchanged restart control was then independently rerun against an archive
of the exact inherited main with only the final ROM/ISO and first integration
test copied in. It passed all first-handoff byte/context/transaction assertions,
then failed at:

```text
firmware_loads_and_executes_actual_disc_bytes_then_cold_restarts_without_ejecting_media ... FAILED
assertion: a cold hardware reset must not eject the physical medium
0 passed; 1 failed
```

The same test, ROM and ISO pass after the fix. Native callers and the browser
could previously remount the medium manually, but an external hardware reset
should not silently discard the host's selected physical disc. This is a reset
boundary defect. Production now retains the immutable medium and reconstructs
all volatile hardware; it does not retain a live CD transaction or its FIFO.
No MMIO error is suppressed, no unimplemented port is whitelisted, and no test
address/ROM signature is recognized by production code.

## Independent executable evidence

The MIT [builder](../tests/fixtures/build_external_startup.py),
[ROM assembly](../tests/fixtures/external-startup.s) and
[disc assembly](../tests/fixtures/external-startup-disc.s) use the repository's
original SH-2 assembler. `--rom-output target/external-startup.bin` emits an
exact 524288-byte raw image; its sparse hex representation is committed.
The original ISO has a Saturn IP and ISO9660 first-read file at LBA21–22.

Only the firmware's instructions issue CD commands, read the 408-byte TOC,
configure the SCU's 4096-byte fixed-FIFO-source DMA, wait for its real completion
interrupt, end the transfer, checksum RAM, establish the stack and jump to RAM.
The host mounts media and reads results; it never copies the executable into
volatile RAM, sets its entry PC or writes its pass record in ExternalBios.

Literal guest records at `06010000` are:

```text
06004004 060FE000 06000000 00000030
00000001 00000001 00000001 00005353
00008000 00000800 41000096 B0000009
```

They represent entry return-PC, actual stack, VBR, computed sum 48, SMPC/DMA0/CD
IRQ counts, independently executing slave mailbox, TVMD, DataEnd 2048-word count,
first TOC entry and loaded first instruction. The success word 600D at `060100FC`
is written by the executing disc guest only after its checks. Native compares
all 4096 loaded bytes against the original disc file. No HLE service pointers are
present. There are exactly three master exceptions and zero slave exceptions.

The firmware's ordered command log at `06010400` contains these literal request
and response tuples; it records guest transactions rather than every bus edge:

| Request CR1–4 | Response CR1–4 |
| --- | --- |
| `0401 0000 0000 0000` | `0180 4101 0100 0096` |
| `0000 0000 0000 0000` | `0180 4101 0100 0096` |
| `0200 0000 0000 0000` | `4180 00CC 0000 0000` |
| `0600 0000 0000 0000` | `0100 00CC 0100 0096` |
| `3000 0000 0000 0000` | `0180 4101 0100 0096` |
| `1080 00AB 0080 0002` | `0400 4101 0100 00AB` |

Both [native assertions](../tests/external_startup.rs) and
[browser assertions](../scripts/external-startup.mjs) check the authored tuples.
The expected values are not generated by executing the emulator. The firmware's
build-time checksum is a media-integrity fence, separate from the literal
context/device/arithmetic oracle.

Six new native tests cover:

- Successful first handoff and a cold restart without remounting.
- No media (`E001`), changed sector operand/instruction (`E002`), and omitted
  device/filter connection (`E001`); none executes the first-read entry.
- Chunks 1/3/17/10000, each with passive CD FIFO/CR4 inspection off/on. At the same
 200000 step attempts, clocks, both complete CPU states and the record/log RAM
  agree exactly.
- Actual guest SYSRES, reexecution from the selected ROM, remount retention,
  fresh IRQ counts and retained 5A backup byte with the remaining 32767 bytes intact.
- Cold reset during an unfinished CD command: clock 0, cleared slave execution,
  fresh CMOK/mask 0/empty FIFO, zero volatile records/executable and successful
  subsequent boot; explicit media clearing produces the no-media error.
- Invalid ROM after success: old executable and records cleared, no usable ROM,
  CPU stopped, ExternalBios still selected, backup and selected medium retained.

The complete unchanged hardware suite also validates before/at/after CD command
latency, rejected busy writes, selector/transfer deadlines, interrupted/restarted
commands and reset cancellation, SMPC SF/system/clock deadlines, SCU masked and
pending sources, DMA data phases and master/slave isolation. Relevant existing
oracles include [CD](../tests/cd.rs), [CD scheduled directory](../tests/cd_directory_schedule.rs),
[clock](../tests/clock.rs), [system reset](../tests/system_reset.rs),
[reset bus](../tests/sh2_reset_bus.rs), [interrupt entry](../tests/interrupt_entry.rs)
and [standby](../tests/standby.rs). Their timing/assertion contracts were not weakened.

The new browser group runs the production Rust→Wasm at `/saturn-rust/`, uploads
neither image, selects both files through the real local pickers in either order,
repeats cold reset and observes the same records/log plus the actual green Canvas

and guest SYSRES controls, checks empty browser storage, and then runs existing
